# Oracle APEX ECharts 1.1.0

Minor release for locale-aware numbers and narrow chart layouts. The ChartSpec
and project-profile contracts remain at 1.0; the server allowlist still rejects
`formatter`, so all formatting stays in the browser runtime.

## Changes

- Numbers on value axes, tooltips, and bar or line labels follow the project
  locale, including the `[x, y]` items that `PK_APEX_ECHARTS` presets generate.
  Before, ECharts wrote `1,299` on axes and tooltips and the raw `1299` on
  labels whatever the locale, and the runtime fell back to `en-US` whenever the
  profile had no locale.
- The locale comes from the profile, then from the page language that Oracle
  APEX writes to `<html lang>`, then `en-US`. Only valid tags that `Intl`
  supports count, so `pt_BR` or `zz` fall back instead of making tooltips with
  a registered formatter throw, as they did in 1.0.x.
- Text tooltip values are shown as they arrive, so a label already formatted by
  the server is not read again as a number.
- Tooltips that can receive a time value keep the ECharts date formatting: a
  time axis without a value axis (such as a schedule by category), or a series
  with `encode.label`.
- Axes without `type` follow the ECharts default: category with `data`, value
  without.
- Charts up to 767 px wide keep axis labels level instead of rotating them 30
  degrees. Category axes skip labels that do not fit, and value axes hide labels
  that would overlap.
- A chart's own `grid` applies at every width. The plug-in grid now applies only
  to charts without one, so value labels beside bars are no longer clipped.
- The installer preflight reads the APEX parsing schema from
  `APEX_APPLICATIONS.OWNER` (#1).

`>=23ai`; the exact evidence and empty live-runtime validation arrays are in
the attached `compatibility.json`.

## Upgrade from 1.0.x

Upgrade the plug-in and `PK_APEX_ECHARTS` together. The new `FILES_VERSION`
changes the plug-in file URLs, so browsers stop using the cached 1.0.0 runtime.
Review charts that relied on rotated labels or on the plug-in grid at narrow
widths; a chart that sets its own `grid` now keeps it.

1. Download and verify `SHA256SUMS`.
2. Agent skill:
   - New installation: extract `oracle-apex-echarts-skill-1.1.0.zip` and run
     `scaffold_consumer.py --ref v1.1.0` first without, then with, `--apply`.
   - Linked 1.0.x skill: run
     `manage_oracle_apex_echarts.py update --ref v1.1.0 --dry-run`, review the
     changes, and repeat without `--dry-run`. The lock then tracks `v1.1.0`.
3. For APEX, run `audit-installation.sql <application_id>` read-only. Until the
   upgrade, the 1.1.0 audit reports a healthy 1.0.x installation as
   incompatible; that is expected.
4. Only in an authorized environment, run `install.sql <application_id>` and
   then `validate-installation.sql <application_id>`, or compile the matching
   package and import `plugin.sql` manually in Shared Components.
5. When several applications share the parsing schema, `install.sql` upgrades
   the first one. For the others, import `plugin.sql` in Shared Components and
   run `validate-installation.sql`.

## Rollback

Follow the
[rollback procedure](https://github.com/andre-simplifica/oracle-apex-echarts/blob/v1.1.0/docs/installation/rollback.md)
with the 1.0.1 artifacts and checksums. The 1.0.1 `install.sql` and
`audit-installation.sql` still read `APEX_APPLICATIONS.PARSING_SCHEMA` (fixed in
#1), so roll back manually: compile the 1.0.1 package, import the 1.0.1
`plugin.sql`, and run the 1.0.1 `validate-installation.sql`.
